Analisi critica REV9 + proposta controllo fasi

Documento di riesame pre-sviluppo · 19/11/2026 · nessun codice · fonte: Guida REV9 + capacità attuali app/script 0.16.73

Risponde alle 4 richieste: incongruenze; bypass ricerca Desktop/Download; indicatori di fase; alternativa a «Continua / Puoi passare…».

1. Esame critico della guida — incongruenze

I1 — Destinazione BT ≠ Desktop (critica alta)
REV9 impone che i 3 file siano sul Desktop anche nel ramo Bluetooth. In Windows, «Ricevi file» Bluetooth deposita tipicamente in «File ricevuti» / Download / cartella scelta dal wizard OPP, non sul Desktop. L’utente deve quindi fare una seconda ricerca+copia non descritta in modo esplicito nel ramo BT (è implicita solo nella verifica Desktop). È la stessa frizione che hai segnalato.
I2 — Overwrite vs «verifica copie precedenti»
La guida dice di verificare che i file siano della sessione corrente, ma non dà un criterio operativo. Con nome (1)/(2) l’utente non distingue: la verifica diventa un vicolo cieco. Contraddice l’obiettivo «una sola versione».
I3 — Casing DATI_CIFS.JSON vs DATI_CIFS.json
REV9 usa .JSON; l’app/script usano .json. Su Windows di solito non conta; su Android/MediaStore può creare ambiguità nella ricerca automatica.
I4 — Fase 3 vs Fase 4 confondono «trasferisci» e «importa»
Parte 1 Fase 3 = solo trasferimento file; import = Fase 4. Parte 2 è coerente, ma nelle proposte UI precedenti l’import è stato mescolato nella Fase 3. Va tenuto un confine netto: arrivo file ≠ interpretazione JSON.
I5 — Parte 2 Fase 1 dice ancora «Scegli Bluetooth oppure USB»
Se l’app ha già fatto scegliere il ramo, ripetere la scelta online è ridondante e rischia di far cambiare metodo a metà. Criterio REV9 («solo il ramo scelto») è corretto: il testo sintetico non deve ripresentare la scelta.
I6 — Checkpoint CIFS lista cartelle non è osservabile da MediaManager
REV9 eleva a «esito atteso» la presenza in lista CIFS Documents Provider. MediaManager non può leggerla. È un checkpoint umano, non automatico: va etichettato come tale, altrimenti si ripete l’errore delle autodichiarazioni finte.
I7 — Controllo finale mescola prerequisiti e risultato
«I 3 file sono sul Desktop» a fine procedura non è un esito utile (possono essere stati spostati/cancellati). Meglio: Catalogo attivato + share raggiungibile.
I8 — Capacità già presenti ma assenti dalla guida
Lo script espone già un annuncio LAN (HTTP/UDP) del bundle a «Tutto pronto»; l’app sa già cercare DATI_CIFS.json in Download/MediaStore. REV9 non li menziona: si perde un’ancora di recupero quando BT/USB falliscono sulla ricerca cartelle.
I9 — Numerazione passi USB (4–7) dopo BT (1–3)
Chi legge solo USB parte dal passo 4. Minore, ma confonde in stampa.

2. Evitare ricerca/copia Desktop e Download — fattibilità

Obiettivo: l’utente non deve «cacciare» cartelle. Una parte avvia, l’altra completa.

Cosa non possiamo fare (limiti reali)

  • MediaManager sul Telefono non vede il Desktop Windows né può forzarvi la copia via Bluetooth OPP.
  • Finché CONFIGURA non è eseguito, sul PC non c’è un agente nostro in ascolto.
  • USB/MTP è pilotato dal PC: l’app Android non può «spingere» file sul Desktop mentre è montata come memoria.

Cosa possiamo fare — proposta a tre leve

LevaDirezioneEffettoNota
A. Esegui dove arriva Telefono → PC Elimina la copia Desktop in Fase 1 BT CONFIGURA già usa la cartella dello script (PSScriptRoot). Istruzione: «Apri la cartella File ricevuti e fai doppio clic su CONFIGURA.CMD». Desktop diventa opzionale, non obbligatorio.
B. Script = maggiordomo PC locale Alla partenza, lo script cerca i 3 file omonimi (Desktop, File ricevuti, Download), li consolida, cancella (1)/(2), scrive solo l’ultima versione Risolve I1+I2 senza chiedere all’utente di navigare.
C. Ritorno dati senza caccia PC → Telefono 1) App in ascolto MediaStore: appena compare DATI_CIFS.json (sessione/token) → «File ricevuto». 2) In parallelo silenzioso: se stessa Wi‑Fi, pull LAN dello script (già esiste). 3) USB: resta copia mirata, ma l’app evita il picker se trova il file in Download. L’utente non cerca Download: l’app lo fa. Il picker resta solo fallback.
Raccomandazione
Non inventare un nuovo protocollo. Combinare A+B+C: BT/USB restano il trasporto; la localizzazione dei file diventa automatica (script sul PC, MediaStore/LAN sul Telefono). La guida smette di dire «vai in Download / Desktop e copia» come passo felice; lo releghiamo a «Se non compare…».

USB

Non eliminabile al 100% senza un tool PC preinstallato. Mitigazione: percorso primario BT + auto-localizzazione; USB documentato come piano B con path fisso e overwrite obbligatorio.

Espediente chiave
Non monitoriamo «il PC». Monitoriamo gli artefatti che il PC deve produrre quando tornano sul Telefono (o via LAN). La Fase 2 resta «in attesa»; il passaggio automatico a «ricevuto» avviene quando compare DATI_CIFS.json valido. Questo assiste l’utente senza checkpoint finti.

4. Alternativa a «Continua / Puoi passare…»

Condivido la critica: quei messaggi non chiudono nulla e non aprono nulla. Propongo un modello a porte.

Modello a porte (una fase alla volta)
  • È visibile solo la fase corrente + lo stato delle precedenti (lampade).
  • Il CTA primario è l’azione concreta della fase, non «Continua».
  • La fase successiva si sblocca solo con evidenza (dove esiste) o con un’azione nominata che avvia il lavoro successivo (non un assenso vuoto).
  • Niente banner «Puoi passare…». Al massimo uno stato: «In corso / In attesa / Completata / Da ripetere».
FaseCTA primario (sostituisce Continua)Sblocco fase successiva
1 Invia set di configurazione (avvia BT/share) oppure istruzioni USB fisse Dopo invio: stato «Inviato — sul PC avvia CONFIGURA». CTA diventa Apri istruzioni script → sblocca Fase 2 (il gate soft è accettabile qui: senza script non esiste artefatto)
2 Solo istruzioni «Doppio clic CONFIGURA» + stato In attesa dei dati dal PC Nessun bottone «avanti». La Fase 3 si apre da sola quando l’app rileva DATI_CIFS (o LAN). Fallback: Non arriva? Rinvia / Importa file…
3 Se file rilevato: Usa questi dati. Se no: istruzione invio da PC + ascolto attivo Import/validazione OK → sblocca Fase 4. KO → «Da ripetere» sulla stessa fase
4 Apri CIFS + Copia campi + Attiva Catalogo Attivazione Catalogo riuscita chiude il wizard. Nessun «Continua» intermedio

5. Sintesi decisioni proposte (per convalida)

  1. Correggere la guida: ramo BT non obbliga Desktop; «esegui dove arriva» + script consolida/overwrite.
  2. Automazione ricerca: PC = script maggiordomo; Telefono = ascolto MediaStore + LAN silenziosa; picker solo fallback.
  3. Indicatori onesti: ambra su invio/attesa; verde solo su artefatti verificabili (file/token/import/attivazione).
  4. Sostituire Continua/Puoi passare con CTA d’azione e sblocco a porte.
  5. Rifiutare (1)/(2) nel happy path; allineare nome a DATI_CIFS.json.
